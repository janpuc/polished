# Design advice from Fable (claude-fable-5-1), 2026-10-25

Read-only advisory on docs/BRIEF.md and the catalog snapshot. The second part was written after Jan answered the open questions.

**Inherited contract (kept):** Python 3.12 + uv + FastAPI + SQLite on a PVC, single container, kopiur backup, bjw-s app-template, Pocket ID via `PocketIDOIDCClient`, ghcr image via release-please, uid 1000, read-only root, `/data` writable, 1 req/s to Shopify, never delete a shade once seen, agents never touch the cluster. Nothing below overturns these. Two things in the brief are wrong in ways that change the design (see 8): the shade count and `updated_at` as a change signal.

## 1. Stack

**Jinja + HTMX + three JS islands (scanner, camera upload, QR/NFC helper), served as a PWA.** One language, no build step, no Node in CI, and the whole app stays one container Jan can leave alone for months. The PWA needs only a manifest and a tiny service worker that caches the shell and static assets; do not do offline writes. Scanner island: feature-detect `BarcodeDetector`, else load a vendored `zxing-wasm` from `/static`. Keep the islands as plain ES modules, no bundler.
*Risk:* iOS Safari camera + WASM quirks eat a weekend; mitigate by shipping name search with autocomplete first so scanning is an accelerator, never the only path.

## 2. Data model

Own integer PKs everywhere; Shopify ids are columns, because gift duplicates and feed drop-outs make Shopify ids a bad identity.

- `product`: every feed row ever seen (526 today). `shopify_product_id`, `variant_id`, `handle`, `product_type`, `raw_json`, `content_hash`, `first_seen`, `last_seen`, `missing_since`.
- `shade`: one row per real single polish, topper, or base coat (372 today: 359 + 9 + 4). `product_id`, `kind` (polish/topcoat/basecoat), `title`, `handle`, `sku`, `hero_image_url`, `retired`, `retiring`, `source` (holotaco/manual, cheap escape hatch for a gifted non-catalog bottle).
- `shade_alias(product_id → shade_id)`: birthday-gift and renamed products point at the canonical shade. 68 of 71 merge by handle automatically, 3 need manual rows (see 8).
- `shade_tag(shade_id, ns, value)`: `finish`, `color`, `collection`. Not a comma string; collection progress and finish-aware dupe check query this.
- `shade_observation(shade_id, seen_at, price_cents, compare_at_cents, available)`: append only when the tuple changes. This is your price/stock/sale history with no daily churn.
- `shade_identifier(kind, value, shade_id, source)` with `kind` in gtin/printed/sku and `source` in catalog/learned. One table covers barcode→shade and P123→shade; it also lets a wrong learned mapping be fixed in one place.
- `bottle(shade_id, printed_code, state, bought_on, price_paid_cents, opened_on, notes, archived)`.
- `wishlist_item(shade_id UNIQUE, priority, note, added_on)`.
- `wheel(id, name, slug, slots=20, archived)` and `wheel_slot(wheel_id, position, stack_id, painted_on, note)`, unique on (wheel, position).
- `stack(id, note)` and `stack_layer(stack_id, ord, shade_id, coats)`. **Own entity, not inline JSON:** "where did I use topper X" is a join on `stack_layer.shade_id`; with JSON you lose the FK and write `json_each` queries nobody wants to maintain. Each slot or mani owns exactly one stack; "copy this stack to a mani" duplicates rows. Do not share one stack row between holders, or editing a wheel slot silently rewrites a mani entry. That is the regret to avoid.
- `mani(id, worn_on, removed_on, stack_id, photo_path, note)`. Photos live under `/data/photos`, resized on upload, so kopiur backs them up with the DB.
- `shade_colour(shade_id, source catalog|wheel, L, a, b, palette_json, image_url, computed_at)`: separate from `shade` so it is recomputable and a wheel-sampled colour can sit beside the catalog one.
- `event(kind, shade_id, payload, created_at, notified_at)`: the in-app "what's new" feed and the alert queue.
- `share_link(token, kind, created_at, revoked_at)`.

Migrations from day one, serendip style, with the build-time self-check in the Dockerfile.

## 3. Swatch identification

Ranked by value/effort for this household:

1. **(a) Barcode + learned mapping: v1.** Cheapest, fits the "do I have this" moment. Seed from per-product `.json` barcodes that validate as GTINs; everything else learned on first scan. Unknown barcode → search → save.
2. **(c) CIELAB dupe check: v2.** Method: prefer the macro image (filenames matching `macro`, 297/405 shades), else the hand swatch (`hand|swipe|swatch`, 332/405), else the hero (346/405). Alt text is null on all 4872 images, so filenames are the only hint and you need a per-shade manual override of the chosen image, with the crop shown in the UI. Centre-crop 50%, drop near-white and near-black pixels by L and chroma thresholds, reject skin in YCbCr (Cb 77–127, Cr 133–173; the "Swatchers" images come from many swatchers, so it must be a range not a point), run a 3-cluster k-means in Lab with Pillow + numpy. Store the dominant Lab plus a 3-colour weighted palette and reuse the catalog `finish:` tags as the finish vector. Distance = ΔE2000 on dominant + min-pairwise palette distance, with a finish-tag Jaccard penalty. Show top five owned shades with thumbnails; the human decides. Holo and multichrome stay lossy, which is why finish tags carry that signal instead of pretending colour does.
3. **(b) Vision LLM label read: v2, only if barcodes disappoint.** Send the photo plus the 372 shade names (a few thousand tokens) and ask for top three. At 9 tok/s the answer is short, so about 5–10 s. Must fail soft when the M3 Pro is off or busy.
4. **(d) Wheel photo → slot colours: v3, as tap-to-sample.** The user taps each slot on the photo and the app takes a median over a small radius. Automatic 20-tip detection with perspective and lighting correction: never.
5. **(e) Mani photo → owned shades: v3**, reusing the tap-to-sample code. Low value; she knows what she wore.
6. **(f) CLIP embeddings: never.** Another model service for a one-maintainer cluster, and it encodes semantics, not colour.

## 4. Auth and exposure

**Pocket ID OIDC in the app (authlib), exposed on `envoy-external` as the mealie pattern, with `AUTH_MODE=oidc|none` for local dev.** The main user is on a phone away from the LAN; an always-on VPN is friction the main user will not tolerate, and a Pocket ID passkey is a one-time setup Jan can do. Deny-by-default middleware: everything except `/healthz`, `/static`, `/share/*` needs a session; allow group `ID-Users`.
*Risk:* a hobby app on the tunnel. Mitigate with no local password path at all and the Pocket ID client scoped to this redirect URI.

**Share link:** `/share/<128-bit random token>`, read-only, renders names, images, prices and the cart permalink only, no bottles or notes, `Cache-Control: no-store`, `noindex`, revocable from the UI. Safe pattern; the downside of a leak is a gift list.

## 5. NFC wheels

Tag URL `https://polished.janpuc.com/w/<slug>` with a short random stable slug (6 base32 chars), not the name and not the autoincrement id. The tag points at the wheel, not the slots, so re-arranging is a DB edit and renaming never invalidates a tag. For a discarded wheel, "move this tag to wheel Y" repoints the slug. Yes to QR stickers: same URL, generated with `segno`, zero extra model, and it covers the laptop and any tag that fails. Tags are written with NFC Tools; the app shows the URL and QR to copy. Pocket ID remember-me keeps the tap-to-open flow one step after the first login.
*Risk:* an authenticated tap on a logged-out phone lands on the login page first; acceptable.

## 6. Catalog sync

In-process asyncio job, daily at 06:00 with jitter, plus a "sync now" button; a CronJob is a second workload for no gain. Steps: 3 `products.json` requests; compute a content hash over title, handle, type, tags, price, compare_at, available, image srcs; upsert `product`; **new shade → one `/products/<handle>.json` fetch for the barcode**, never again (barcodes are static). Day one is ~372 requests over about seven minutes at 1 req/s. **Do not use `updated_at`**: all 526 products carry `2026-10-25` today, so it changes daily and would refetch everything.

State: `collection:retirement` → retired (117 today; 115 unavailable, 2 still buyable); `collection:soon-retiring` → retiring (14); absent from the feed three syncs running → `missing_since`, never deleted; unavailable without a retirement tag → sold out (60 today, your "back in stock" candidates). Sale = price < `compare_at_price`, which exists on 404/405 shades; 44 are on sale right now. New collection = a `collection:` tag with no prior shade, or `published_at` after the last sync.

Alerts, minimum: an in-app "what's new" page from `event`, plus one daily Matrix message via the existing bot, sent only when there are events and only for wishlist back-in-stock, wishlist sale, wishlist retiring, and new shades. Matrix because the household already reads it; ntfy means another app on the main user's phone, email gets ignored. Keep the notifier a single function behind a webhook env var so swapping is trivial.

## 7. Staging

- **v1:** catalog sync and shade list with search and finish/colour/collection filters; per-shade own/wishlist toggles with bottle count and state; wishlist with total and cart permalink; barcode scan with learned mapping; PWA shell; Pocket ID; kopiur. Cut: photos, wheels, stacks, colour, alerts, mani log.
- **v2:** wheels + slots + stacks with NFC/QR; colour extraction and dupe check; observations and Matrix digest; collection progress; share link; vision fallback if barcodes fail in practice.
- **v3:** mani log with photos, tap-to-sample colours, random picker, "not worn in a while".
- **Never:** CLIP, automatic wheel detection, Web NFC writing, an SPA.

## 8. Brief corrections

- **Shade count:** 46 of the 405 "Nail Polish" products are bundles (tagged `bundle:product`; 5 even have numeric SKUs like `44045797130330`). Real singles are 359 polish + 9 top coats + 4 base coats = 372.
- **Toppers are `product_type: Top Coat`** (flakie tacos, unicorn skins, scattered/linear holo). Skipping non-polish types would break the layers feature. Include Top Coat and Base Coat; skip the rest.
- **Birthday gifts do not merge by SKU.** `im-over-brew-birthday-gift` is `HL-00026-HB`; the real shade is `HLT-NP-0921-THET-B04-R`. Only 36 of 70 gift numbers coincide with any `HL-*-NP` number, and SKU digits are not unique anyway (`HT-00087-ST` bundle vs `shady-navy` `HL-00087-NP`). Merge by handle; manual aliases for `aurora-unicorn-skin` (a Top Coat), `linear-holo-taco™` (trademark glyph in the handle) and `royal-tea-blue` → `royal-tea-blue-2021`.
- **P123 ↔ SKU digits can only hold for the 284 `HL-*-NP` shades**; 75 older `HLT-NP-…` shades carry no shade number. Open question 1 stays open, and `shade_identifier` handles it either way.
- **`updated_at` is useless** for change detection (above).
- **Images:** 5 to 48 per shade, median about 11, all alt text null; filename conventions differ per collection (Brainrot has unnamed `15.png`). Plan on a manual image override.
- **Missing from the brief:** `compare_at_price` and `collection:soon-retiring` give sale and retiring alerts for free; photo storage and backup; a `source=manual` escape hatch for non-catalog bottles; the main user's OS also decides NFC writing and PWA behaviour, not only scanning.

**Risks still open:** whether printed barcodes scan and match anything (decides v1 scanning value), the main user's OS and Pocket ID account, the Matrix bot's send API. **No executor handoff warranted yet**; the next step is Jan answering open questions 1 to 4 and a `docs/DESIGN.md` from this.

**Addendum after Jan's answers.** The core recommendation stands; these refine 2, 3, 4, 5, 7 and add the layer UX.

**Identifiers (answers 1).** Confirmed in the snapshot: Spirit Fingers is `HL-00169-NP` and no shade carries `HL-00259`, so P numbers are independent of SKU digits. `shade_identifier` stays the single learned table with kinds `gtin`, `printed`, `sku`. Seed `gtin` rows at first sync from per-product `.json` barcodes that validate as GTIN (expect most of the 284 `HL-*-NP` shades; the 9-digit Brainrot values fail the check and are dropped). Normalize every scanned and seeded code to GTIN-13 before lookup, because ZXing returns a UPC-A either as 12 digits or as an EAN-13 with a leading zero. Capture the P code when a bottle is added: the "add bottle" form has one field, and typing `259` into the global search also hits learned printed codes before falling back to name search. That gives the main user a scan-free identification path that costs nothing.

**iPhone only (answer 2).** Scanner island is `zxing-wasm` only; keep the `BarcodeDetector` feature-detect as a two-line branch but do not test it. `getUserMedia` works in Safari and in home-screen PWAs since iOS 13.4; keep `<input type=file capture>` as the photo path. One iOS fact changes the NFC flow: a tag tap opens Safari, not the installed PWA, and iOS keeps separate cookie jars for the two. So the main user logs in to Pocket ID once in Safari and once in the PWA. Set a long app session (30 days, rolling) and rely on Pocket ID remember-me so this happens rarely. QR stickers stay the fallback; the iOS camera app reads them natively.

**Exposure (answer 3).** Settled: `envoy-external`, Pocket ID OIDC in the app, `ID-Users` allowed, the main user already has an account. Nothing else changes.

**Public repo (answer 5).** Config only via env; the OIDC client secret arrives from the operator-written Secret; `.gitignore` the SQLite file, `/data`, photos and any `.env`. Keep `research/p*.json` out of the repo or trim them to a few products as test fixtures; they are public data but 4 MB of noise. Jan's call whether first names stay in `docs/BRIEF.md` once public; the app itself stores no personal data beyond Pocket ID subject ids.

**Layer stack UX on a phone (answer 4).** Concrete recommendation:

- **Mental model: painting order.** Layers listed top to bottom in the order they were painted, labelled Base, 2nd, 3rd, Top. Summary rendered everywhere as `One-Coat Black + Spirit Fingers ×2 + Flakie Holo Taco`, left to right matching Jan's "x + y + z". Chips carry a colour dot from `shade_colour` when present, else the hero thumbnail.
- **Builder is a bottom sheet with one search field, autofocused.** Results ranked: owned shades first, then wishlist, then catalog. Filter chips: Owned, Toppers, All. Tap a result = append a layer and keep the sheet open, so x + y + z is three taps plus typing. The field also accepts a P code or a scan button.
- **Default coats by kind:** 1 for toppers (kind `topcoat`, or `finish:flakie|glitter` with `color:clear`), 2 for polish. A `−  2  +` stepper sits on each row.
- **Reorder with up/down arrows, remove with an ×.** No drag-and-drop: it is flaky on mobile Safari and fights HTMX. With two to four layers arrows are faster anyway.
- **Templates:** an "over black" button that inserts One-Coat Black as base, "copy stack from…" that picks any wheel slot or mani, and "duplicate last stack". Toppers are mostly swatched over black, so the first template covers the common case in one tap.
- **Implementation:** the sheet is one HTMX partial. Opening a slot or mani creates or loads its draft `stack` row; every tap posts and re-renders the layer list; Save commits, Cancel deletes the draft. No client-side state, so a dropped connection or a backgrounded tab loses nothing. Each holder owns its own stack rows, so editing a slot never alters a mani.
- **Display name:** auto-generated from the layers; optional user name field for favourites.

**Staging change.** Jan calls layers the best part, so the search-sheet component ships in v1 as the shade picker for bottles and wishlist, and wheels + stacks become the first v2 item rather than one of several. v1 scope otherwise unchanged.

**Risks now:** UPC normalization edge cases, the Safari-versus-PWA double login, and whether ZXing reads the small bottle barcode reliably under phone lighting. Still no executor handoff; next step is `docs/DESIGN.md` from the two messages combined.
